# P0.1 - Skeleton and domain model

## What was built
- Gradle multi-module skeleton; the root build FAILS if a service depends on a sibling service.
- Three Postgres schemas via Flyway (`trade`, `logistics`, `pricing`), one migration directory each.
- JPA entities for every table, plus repositories. No behaviour yet.
- Nested refs (`TradeRef`, `QuotaRef`, `AssignmentRef`) as plain Java in `contracts`.
- 14 tests: 4 pure unit tests, 10 Testcontainers tests on real Postgres.

## Read in this order
1. `contracts/.../refs/TradeRef.java`, `QuotaRef.java`, `AssignmentRef.java`, then `RefsTest`
2. `services/trade/src/main/resources/db/migration/trade/V1__trade_schema.sql`, then `Trade`, `Quota`
3. `services/logistics/.../V1__logistics_schema.sql`, then `QagRevision`, `QagRevisionMember`
4. `services/pricing/.../V1__pricing_schema.sql` (the sharing table and the immutability trigger), then `QuotaRevisionMember`
5. `build.gradle.kts` (boundary check)

## Decisions and why
1. **Nested text refs (1 / 1.1 / 1.1.1).** A ref carries its ancestry, so logs, events and support conversations need no lookup. Cost: text sorts lexicographically (`1.10` < `1.2`), so ordering uses the numeric `compareTo` or the `seq` column, never `ORDER BY quota_ref`. A test pins this trap.
2. **Schema per service, no cross-schema foreign keys.** `quota_ref`, `qagr_id` are references by value. Cost: no database-enforced integrity across services; benefit: each service can be deployed and migrated on its own.
3. **Insert-only revisions, enforced twice.** Hibernate `@Immutable` stops our code; a Postgres trigger stops everyone else. This is what keeps replay deterministic. A test proves raw SQL UPDATE/DELETE fails.
4. **Constraints in the schema where they are cheap and local** (positive quantities, unique `(trade_id, seq)`), **rules that are business logic stay in domain code** (sum of quota qty = trade qty is deliberately not a trigger).
5. **`ddl-auto=validate`.** Flyway owns the schema; Hibernate only checks the entities match. Drift fails a test, not production.
6. **Enforced module boundaries in the build**, even though everything runs in one JVM later. It is the cheap way to keep the option of splitting services.

## Likely follow-up questions
- *Why not one shared database schema?* Ownership and independent deployment; the target is a schema per service on one Oracle estate with no cross-service joins.
- *Why UUIDs for revisions but BIGSERIAL for trades?* Revision ids are generated by the writer before insert, so it can build a whole tree without round trips and the ids travel in events.
- *Where are the indexes for as-of lookups?* `(quota_ref, brd, created_at DESC)` on both revision tables, and `(assignment_ref, content_hash)` for the sharing lookup.
- *Postgres vs Oracle?* Same SQL for everything the demo exercises; HCC, Smart Scan and partition compression are absent and nothing here depends on them.

## Not built (on purpose)
Behaviour: quota derivation, QAG diffs, outbox, hashing, writers, gateway (P0.2 onwards). Lots, inventory, deals (designed only).

## Environment gotchas found (worth knowing)
- Docker 29 rejects API < 1.40; the Testcontainers version managed by Spring Boot 3.3.4 is too old, so `gradle/jpa-service.gradle.kts` pins 1.21.4.
- The JDBC driver sends the JVM timezone to Postgres; a legacy alias such as `Asia/Calcutta` fails to connect, so tests run with `-Duser.timezone=UTC`.
