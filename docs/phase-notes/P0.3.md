# P0.3 - Pricing with structural sharing (the headline)

## What was built
- **Domain (plain Java):** `AssignmentContent`, `ParameterContent`, `PriceComponentContent`, `ContentHasher` (bottom-up SHA-256),
  `FixationPolicy`, `EventApplier`, `BrdGuard`, `Decimals` (fixed scale).
- **Two writers behind one interface:** `RevisionWriter` -> `CopyAllRevisionWriter` (legacy baseline) and
  `StructuralSharingRevisionWriter`, chosen by `commodity.pricing.revision-strategy`.
- **`RevisionStore`:** batched insert-only JDBC writes, and the as-of resolution reads.
- **Pricing service + API:** price components (409 on over-fixation), parameters, approval, `GET .../pricing?asOf=`, revisions, fixation.
- **Consumer:** `logistics.qag.revision.v1` -> pricing revision, with eventId dedup, 3 retries, then `<topic>.dlq`.
- **Benchmark:** `./gradlew :benchmark:run`.
- **Also (owner rule):** logistics now refuses quantity edits while a fixation exists (`FixationDirectory` port, HTTP adapter in `platform`).

## The measured result (say these numbers, they are real)
| Assignments changed | Copy-all rows | Sharing rows | Ratio |
|---|---|---|---|
| 1 | 301 | 35 | 8.6x |
| 2 | 301 | 49 | 6.1x |
| 5 | 301 | 91 | 3.3x |
| 20 | 301 | 301 | 1.0x |

That is 88% fewer rows for one changed assignment, consistent with "roughly 90%". The 1.0x row is the honest one. The spec's
illustrative 960/48 did not match its own schema, so the exit criteria were corrected to these measured figures.

## Decisions and why
1. **Content-addressed sharing.** An assignment's hash covers its own fields plus its children's hashes; equal hash means equal content, so
   an unchanged assignment reuses its row. Correctness comes from hashing, not from trusting the event's diff: a wrong diff cannot produce a
   wrong revision.
2. **Hashing details that each prevent a silent bug:** sorted children (order cannot cause a false difference), fixed-scale decimals
   (10.0 == 10.00), length-prefixed fields (no concatenation collisions), null distinct from empty, type tags per level.
3. **Both writers kept, behind one interface and a config switch.** The legacy writer is the control for the benchmark and the property, and an
   escape hatch: sharing can be switched off without a release.
4. **The equivalence property is the test that matters.** Random quota (5-30 assignments, 0-15 parameters, 1-5 components) and random history
   (1-20 mutations, including no-ops and same-BRD revisions), resolved at every BRD touched, compared with an in-memory model AND across strategies.
   A deliberately broken writer (reuse by ref only) is caught within a few seeds, so the property has teeth.
5. **Immutable rows make sharing safe.** Insert-only (trigger-enforced) means no revision can change what a shared row means for another.
6. **Write path is JDBC batches, not JPA.** Hundreds of rows per revision with client-generated ids; batching collapses round trips
   (lever 4). Resolution SQL is written out because it is the join the design describes.
7. **Approval is its own insert-only record** (owner decision), so approving never cuts a revision.
8. **Delivery guarantees:** at-least-once + dedup marker written in the SAME transaction as the revision; 3 retries then DLQ; a bad record
   never blocks its partition.
9. **Derived values are never stored:** priced, unpriced and over-fixed are computed on read (and the tests found a scale bug there: an empty
   sum reported `0` instead of `0.0000`).
10. **Per-quota advisory lock** for read-decide-write (chain, over-fixation), same reasoning as logistics; the concurrency test shows two
    simultaneous 60-of-100 fixations yield exactly one 201 and one 409.

## Likely follow-up questions
- *Why is it only 8.6x and not 20x?* The 20 member links are written on every revision whatever changed. The saving is bounded, and that is
  the honest limit of this model. A tree of buckets or delta-plus-checkpoint links would cut it further at the cost of a more complex read.
- *What does sharing cost you?* Reads become joins across revisions (indexed, three queries), purging a revision can no longer delete its
  children blindly (archive whole quota subtrees, hence partitioning by BRD), and a hash bug would silently corrupt history, which is why the
  property test exists.
- *Could two revisions ever disagree on a shared row?* No: rows are insert-only, enforced by a trigger, not only by convention.
- *What if the event's diff is wrong?* Nothing breaks: hashing decides what is shared. The diff is a hint and a contract for other consumers.
- *What if the same event arrives twice?* Dedup on eventId, in the same transaction as the write.
- *What happens to a fixation if logistics reduces the quantity?* Logistics refuses while a fixation exists. If a race gets past that check,
  pricing applies the event and flags the assignment over-fixed (derived), rather than stalling behind logistics.
- *How would you scale this to the full population?* Partition revisions by BRD, compress closed partitions, keep the blotter off the system of
  record, and put pricing inserts per QAG revision on a dashboard as a headline SLI.

## Not built (on purpose)
Replay endpoint and valuation (P0.4), blotter and SSE (P0.5), the app module that runs everything in one JVM (P0.5), using the event diff to skip
hashing unchanged assignments (a read-side optimisation: it would avoid loading unchanged subtrees, at the cost of trusting the diff).
The P0.1 JPA entities remain as the schema-validated mapping of the tables; the write path uses JDBC.

## Environment gotchas found
- jqwik has no Testcontainers integration, so the non-Spring tests share one container through a singleton (`PricingTestDb`).
- The 40-try property takes about 35 seconds; that is the cost of running it against a real database, and it is worth it.
