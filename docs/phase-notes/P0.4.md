# P0.4 - Valuation gateway

## What was built
- **valuation-gateway service:** durable request state, deterministic request key, result cache, in-flight de-duplication, per-lane limits, dispatcher,
  reply handler that correlates through the database, watchdog, request browser API.
- **Stub engine adapter** (`services/stubs`): consumes `valuation.request.v1`, replies on `valuation.reply.v1`, deterministic value, failure knob. Depends on
  no other service.
- **Reference data stub:** `FunctionalLineDirectory` (cutover date + explicit override); trade gained an optional `functionalLine`.
- **Pricing:** `GET /api/valuation-inputs` (immutable ids as the request key inputs) and `POST /api/replay`.
- **Contracts:** `ValuationRequested`, `ValuationCompleted`, `ValuationInputs`, and the ports `ValuationInputsProvider`, `ValuationSubmitter`, `FunctionalLineDirectory`.

2. `gateway/service/ValuationService.java` (the submit flow and why each step is in that order)

## Exit criteria and the test that proves each
| Criterion | Test |
|---|---|
| Same inputs produce the same request key | `RequestKeyTest.sameInputsProduceTheSameKey` |
| Submitting the same request twice calls the engine once; the second returns from cache | `GatewayFlowTest.submittingTheSameRequestTwiceCallsTheEngineOnce` |
| Killing the gateway mid-flight and restarting completes the request from durable state | `GatewayRestartTest` (both a SENT and a PENDING request) |
| A request whose BRD is closed for that desk is rejected | `GatewayFlowTest.aClosedBrdIsRejectedUnlessRestatedAndACachedAnswerIsStillServed` |
| Saturating BULK leaves an INTERACTIVE request inside its timeout | `GatewayLanesTest.saturatingBulkLeavesInteractiveInsideItsTimeout` |

## Decisions and why
1. **The request key is a pure function of immutable ids.** Pricing works off immutable revisions, so a valuation depends only on ids and dates. Same key,
   same answer, forever: retries are free, duplicate triggers collapse, replay is a cache hit.
2. **Correlate through the database, never memory.** Any instance can handle any reply; a killed gateway loses nothing. Proven by restarting a whole
   Spring context and having the second one finish the first one's request.
3. **Every state change is compare-and-set** (`UPDATE ... WHERE status = 'SENT'`). Duplicate replies, a watchdog racing a late reply and several instances
   are safe with no in-memory coordination.
4. **Lane isolation is a concurrency limit, not a rate limit.** A bulk sweep can fill only its own in-flight budget. Excess requests wait as PENDING rows in
   the database (durable), and the dispatcher queries per lane so a bulk backlog cannot hide interactive work.
5. **Order of checks matters.** Cache before the closed-BRD check, so replaying a past date is a cache hit, not an error or a recomputation.
6. **A lock on the request key** makes check-then-insert safe: two identical submissions together cannot both start work.
7. **The engine adapter is self-contained.** The request carries all inputs and the adapter looks nothing up. That is the one thing this design changes
   outright from the legacy interface, and here it is visibly true: the adapter's module depends on no other service.
8. **Routing is reference data.** The functional line decides the engine, by cutover date with an explicit override. Retiring an engine is a data change.
9. **Slots are taken before the dispatch transaction and returned after it**, so a rolled-back dispatch cannot leak a slot.
10. **Failure policy reused:** the reply consumer retries then dead-letters, so a malformed reply never stalls replies (shared `DlqErrorHandler`).

## Likely follow-up questions
- *Why is idempotency possible at all?* Because inputs are immutable revision ids. A mutable-state design cannot promise "same key, same answer".
- *What if the gateway dies with requests in flight?* They are rows in the database. The restarted instance seeds its lane budget from the SENT rows,
  and the reply, when it arrives, is correlated by requestId in the database.
- *What if the engine never replies?* The watchdog (every 10s in the default config) retries after the lane timeout, up to 3 sends, then FAILED with the reason.
- *What if two identical requests arrive together?* One wins the key lock; the other sees it and gets the same requestId back.
- *How do you stop a market-data sweep starving a trader?* Separate in-flight budgets per lane. TARGET: separate topics and consumer groups per lane, and
  limits that adapt (AIMD) to engine latency.
- *Why is the closed-BRD rule enforced here too?* Valuations are produced here, so the closed-date rule belongs at the point where they are produced.
- *Why a direct Kafka send from the engine adapter when the rule is "always the outbox"?* It has no database, so there is nothing to be atomic with; a lost
  reply is recovered by the watchdog.
- *Does the key change when I reprice an unrelated assignment in the same quota?* Yes, because the key includes the quota revision id, even though the
  assignment's own ids are unchanged by structural sharing. Dropping pqrId from the key would let sharing carry into the cache; it stays because the spec
  defines the key that way. This is a good improvement to volunteer.

## Known limits (say them first)
- The lane counter is in memory: correct for one gateway instance (seeded from the database at startup), not across several. TARGET: derive it from the
  durable table or a distributed semaphore.
- One shared request topic, so lane isolation is enforced at the gateway, not in the broker. TARGET: a topic and consumer group per lane.
- Retries hold the partition briefly (fixed back-off); TARGET: non-blocking retries on delay topics.
- A late reply after the watchdog retried is ignored, so that request may cost one extra engine call.
- Replay of an older revision that a newer one superseded on the same BRD is refused; supporting it needs the input port to accept a revision id.
- No circuit breaker on engines and no shadow mode yet (both designed: fast explicit failure for interactive callers; run both engines and compare before retiring one).

## Not built (on purpose)
Market data revaluation (Jupiter-side), shadow mode, the app module that runs everything in one JVM (P0.5), a real engine.

## Environment gotchas found
- Each gateway test class starts its own Postgres and broker, and closes its Spring context afterwards, so contexts never share consumer groups
  (a second live instance would consume the first one's replies and skew the in-memory lane counter, which is exactly the multi-instance limit above).
- The fake engine is a plain Kafka consumer outside the gateway's context, so it survives the restart test.
