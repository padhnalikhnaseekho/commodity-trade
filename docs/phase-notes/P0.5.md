# P0.5 - Blotter and demo harness

## What was built
- **`services/blotter`:** a disposable read model built from pricing's quota snapshots and the gateway's valuation results; as-of query; live change stream over SSE.
- **Events added:** `pricing.quota.published.v1` (pricing, through its outbox) and `valuation.published.v1` (gateway, through its outbox).
- **`app` module:** one Spring Boot application; each service behind its own profile; a per-schema Flyway runner; the composition root with no business code.
- **`demo-seed`:** a deterministic generator that drives the running application through its public API: 50 trades across four business lines and three desks.
- **`ui`:** an Angular 17 blotter (standalone components, signals, `EventSource`) with a desk filter, an as-of date picker, provisional badges and live row highlighting.
- **`AppEndToEndTest`:** the real seed against every service on real Postgres and a real broker, checked through the public APIs.
- **A real bug found and fixed:** revision ordering by wall-clock time (see decision 9).

## Decisions and why
1. **Profiles, not just packages.** Each service is a Spring profile loaded by one entry class; the app scans nothing. A service outside the profile list contributes no beans,
   endpoints, consumers or schema. Proven by starting each subset. Honest limit: the clock and reference data are in-process stubs, so a process running a service that needs
   them also runs `stubs`.
2. **A per-service migration runner** instead of Spring Boot's single Flyway: each service migrates only its own schema, and JPA waits for every active service's migration.
3. **The blotter is a projection, not a source of truth.** Upserts are idempotent (a replayed event, or a replay of the whole topic, gives the same table), so it needs no dedup
   table; it can always be rebuilt from the event streams. It stores derived priced/unpriced because it IS a read model (the rule "never store derived values" protects
   pricing's revision tables from write amplification).
4. **Changes are pushed only after commit**, so an open screen never shows something that then rolls back.
5. **Deltas, coalesced.** A row that changed nine times in a second is pushed once, and a test shows the merged patch equals applying all nine in order.
6. **SSE with resume.** Plain HTTP, one direction, browser reconnects by itself; a bounded replay buffer answers `Last-Event-ID`, and a `reset` tells a client that fell too far behind to refetch.
7. **Provisional is derived at read time** from the current approval state, so approving an assignment flips the flag with no valuation recomputed.
8. **The seed goes through the API**, so it proves the whole write path, and it depends on no service module.
9. **Order by the insertion sequence, never by a timestamp.** The end-to-end test failed intermittently. Exact per-assignment expectations and a database snapshot showed the API
   resolving to an older revision than the write path's head, because later rows carried earlier `created_at` values (the wall clock went backwards). The spec's
   `created_at` tie-break was replaced by `brd DESC, id DESC` in pricing revisions, approvals and QAG revisions, with migrations and regression tests.

## Likely follow-up questions
- *Why not just run separate processes?* For a five-minute demo it is more setup and more failure modes. The structure and a test make splitting a change of profile and URLs.
  What I would say it hides: real network failure, database-per-service, and the in-process stubs.
- *How does the blotter stay correct if it misses an event?* It is rebuilt from the streams; upserts are idempotent; a client that misses pushes is replayed or reset.
- *Why SSE and not WebSockets?* The data flows one way, it is plain HTTP with automatic reconnection, and `Last-Event-ID` gives resume.
- *How is the as-of view computed?* Latest row per assignment with `brd <=` the date, the same rule as everywhere else in the platform.
- *What was the hardest bug?* The revision ordering by timestamp (decision 9): it looked like a concurrency bug, tracing ruled that out, and the data showed the clock.
- *Why is the RM valuation on every row?* An RM quota is valued at quota level and no allocation rule exists, so the same number is shown on each row and marked as quota level.

## Not built (on purpose)
Authentication, a separate SSE tier, real reference data and business day control, shadow mode for engine retirement, the mirroring projector and later services.

## Environment gotchas found
- WSL2 mirrored networking narrows the ephemeral port range to about 4,100 ports. Widening it broke loopback connections (a source port outside the working range fails), so it
  must not be changed. Docker's random host-port picks then collide with sockets in TIME_WAIT, so container starts are retried and Testcontainers' cleanup helper is disabled.
- Testcontainers versions managed by Spring Boot 3.3 are too old for Docker 29; the pinned override lives in `gradle/jpa-service.gradle.kts`.
